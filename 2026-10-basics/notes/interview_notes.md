## 1. 高频考点（★ 越高越必须）

★★★ = 跨公司跨方向重复出现，答不出直接挂；★★ = 单方向高频；★ = 加分项

### ★★★ Transformer 基础（W6—W8 覆盖，最高优先级）

| 题 | 30 秒口述要点 | 日历 |
|---|---|---|
| 为什么除以 √d_k | q·k 各分量独立同分布时点积方差 = d_k，d_k 大则 softmax 输入过大 → 单点概率趋 1 → **梯度趋 0**。除以 √d_k 把方差拉回 1。是**数值稳定性**，不是防过拟合 | W6 ✅ |
| 为什么要多头 | 把 d_model 切成 h 份，在不同子空间并行做注意力，捕捉不同类型依赖（语法/指代/位置），最后拼接 + W_O 融合。**参数量不变**：d_model=4 时单头 64 个参数，h=2 双头仍是 64 | W6 🔵 |
| Q/K/V 从哪来 | 同一输入 X 经三个独立线性投影：Q=我找什么、K=我是什么、V=我传什么 | W6 ✅ |
| cross-attention 的 QKV 来源 | Q 来自 decoder 上一层，K/V 来自 encoder 输出 | W7 |
| 三个注意力各自要不要 mask | encoder self-attn：只有 padding mask；decoder self-attn：causal + padding；decoder cross-attn：只有 padding（K/V 来自 encoder，全可见） | W7 |
| 为什么位置编码用加法不用拼接 | 拼接让 d_model 翻倍、参数和计算都涨；加法不增维。正弦编码各频率分量与词嵌入相加后，仍可被后续线性层区分 | W7 |
| 为什么用 LN 不用 BN | 序列变长 + padding 让 BN 的跨样本统计量不稳；BN 推理依赖 running stats，小 batch 不准。LN 在**单样本单位置**上归一化，训练/推理一致，与 batch 无关 | W7 |
| LSTM 何时比 Transformer 好 | 数据量小、序列短、强时序依赖时；Transformer 缺归纳偏置，要更多数据；但 LSTM 不能并行，慢 | W7 |

### ★★★ RL 对齐家族（**日历缺口**，见第 3 节）

| 算法 | 一句话区别 | 关键细节 |
|---|---|---|
| PPO | 有 critic，clip 约束，GAE 估优势 | clip 系数调大→不稳，调小→学不动；clip 与 KL 约束**不等价**（显式约束 vs 隐式正则） |
| GRPO | 去 critic，同一 prompt 采样 G 条，**组内归一化**算优势 A_i=(r_i−mean)/std | 前提：组内方差可控；省掉 critic 显存，但采样成本上升 |
| GSPO | **序列级**重要性采样 | 多轮/长序列场景更稳 |
| DPO | 无需 reward model，用偏好对直接优化策略 | 隐式 reward = β·log(π_θ/π_ref)；**reference model 是锚点**，防止偏离 SFT 分布、保住语言能力 |
| DAPO / DSPO | token 级损失 / clip-higher / 序列级优化 | clip-higher 对高优势 token 放宽上限 → 提升探索 |
| OPD（在线策略蒸馏） | 学生采样、老师打分 | on-policy，靠 KL 控制漂移 |

**必背判断**：DPO 是离线偏好优化（不采样、无 RM）；GRPO/PPO 是在线 RL（要采样、要 reward）。面试常问"DPO 能否替代 GRPO"——不能，复杂推理/探索仍需在线 RL。

### ★★★ 可验证性四连问（每场面试都会以不同形式出现）

1. 指标口径谁定的？怎么统计的？
2. 评测集从哪来？和训练集有没有重叠？
3. 同期还上线了什么？怎么排除它们的功劳？（混淆变量）
4. 有没有做消融？基线怎么设？每个阶段边际收益多少？

> **答法**：先说口径 → 再说样本量与随机种子 → 再说对照设计 → 最后承认局限。承认"没做过"比硬编得分高。

### ★★ LoRA / 量化（W10）

| 题 | 要点 |
|---|---|
| LoRA 原理 | W = W₀ + BA，B∈ℝ^{d×r}、A∈ℝ^{r×d}，r≪d；只训 B、A，推理可合并回 W |
| **LoRA 为什么没有激活函数** | BA 本身是低秩**线性**增量。加激活后：① 破坏"对原权重施加低秩线性扰动"的假设；② 推理时无法合并成单个 W₀+BA，失去"零额外推理延迟"这个最大卖点 |
| alpha 作用 | 实际缩放 = alpha/r；alpha 大则增量占比大、更激进 |
| target_modules 怎么选 | 一般 q_proj/v_proj 起步，效果不够再加 k/o 与 MLP；全加参数变多但通常效果更好 |
| 4-bit（QLoRA）与计算 dtype | 权重以 NF4 存 4-bit，计算时反量化到 bf16；省的是**存储显存**，计算精度不降 |
| MHA / MQA / GQA 的 KV cache 差异 | MHA：2·L·N·h·d_head；MQA：所有头共享 1 份 K/V → 1/h；GQA：G 组 → G/h。牺牲的是表达力/效果，换显存与吞吐 |

### ★★ 推理服务（W19—W22）

| 题 | 要点 |
|---|---|
| KV cache 为何省计算不省显存 | 缓存历史 K/V 避免每步重算 → 省计算；但显存随序列长度 N **线性增长**，且随并发数线性增长 |
| KV cache 显存公式 | 2（K 和 V）× L 层 × N 序列长 × h 头 × d_head × 字节数 |
| PagedAttention 解决什么 | KV cache 连续分配的**内存碎片**与预留浪费；用分页块表按需分配，显存利用率从 ~60% 提到 ~95% |
| 连续批处理（continuous batching） | 不等整批结束，请求完成即退出、新请求立即插入 → 提升吞吐、降排队延迟 |
| 首 token 延迟 vs 端到端延迟 | TTFT 由 prefill 决定（算力密集）；TPOT/端到端由 decode 决定（显存带宽密集）。优化手段完全不同 |

### ★★ RAG（W15—W16）

| 题 | 要点 |
|---|---|
| 分块策略 | 固定长度 / 递归 / 语义 / 结构化（按标题、表格）；用 chunk 256/512/1024 做对照，看 Recall@5 |
| 提升回答正确率 | 混合检索（BM25+向量）、重排（rerank）、多路召回、查询改写 |
| Lost in the middle | 关键信息放首尾 + 重排，别依赖中间位置 |
| 表格/图片解析 | 结构化解析成 markdown 表格再切；图片走多模态模型转文字 |
| 评测三分法 | 事实题 / 跨段落题 / 不可回答题各 1/3；指标 Recall@5 + 答案正确率 + 引用准确率 |

### ★★ Agent（W17—W18）

| 题 | 要点 |
|---|---|
| Harness 是什么 | Agent 的运行外壳：Loop（感知-决策-行动-观察）、工具、沙箱、记忆、上下文管理、错误处理 |
| 工具调用失败怎么兜底 | 重试（指数退避）→ 降级（换工具/静态兜底）→ 熔断 → 终止并拒答；必须设**重试上限 + 最大步数** |
| 参数类型对但业务含义错 | 加**业务语义校验层**（范围、单位、外键存在性），不能只靠 schema |
| 置信度阈值为什么不能直接用模型概率 | 概率**未校准**；要用验证集做校准（温度缩放 / isotonic），或改用可验证信号 |
| 记忆机制：Markdown vs RAG | Markdown 是结构化上下文（始终在窗口内，可人读可 diff）；RAG 是向量检索（量大但可能召不回）。二者互补，不是替代 |
| 多 Agent vs Workflow | 动态编排（路径不固定）vs 静态流程（路径确定、可预测、便宜）。能用 Workflow 就别上多 Agent |
| Agent 可观测性 | 请求 ID、每步留痕、失败回放、链路归因（规划/工具/表述三类分桶） |

### ★ 其他方向的"可迁移一题"

- **图像生成**：classifier guidance vs classifier-free guidance（是否需要额外分类器；CFG 用条件/无条件联合估计）
- **DDPM vs DDIM**：随机采样 vs 确定性采样，DDIM 是 DDPM 的推广，可跳步加速
- **SAM 为何强**：数据引擎 + 大规模掩码预训练；prompt 有点/框/掩码/文本

## 5. 面试方法论（5 条，来自面经第 9 节）

1. 把「效果怎么证明」当必答题，提前写好：成功率、评测集来源、标注规则、失败归因。

### 三个必须补的缺口

#### ① 压测「通过标准」（最狠的一问）

W19 验收写的是「均可复现；记录首 token 延迟与端到端延迟」，W21 写的是「连续压测 10 分钟无崩溃；报告 p50/p95、显存峰值、失败率」——**这些是产出物，不是标准。**

标准长这样（SLO，Service Level Objective，服务水平目标）：

| 指标 | 阈值 | 为什么是这个数 |
|---|---|---|
| p95 TTFT（首 token 延迟） | < 800 ms | 超过 1 s 用户会明显感到"卡住了" |
| p99 端到端 | < 8 s | 交互式问答的容忍上限 |
| 错误率 | < 1% | 低于这个数才不需要重试逻辑 |
| 吞吐 | >= N tok/s | N 由 W19 单请求实测基线定 |
| 显存峰值 | < 卡容量 × 0.9 | 留 10% 防 OOM |
| 连续 10 分钟 | 不崩溃、错误率不随时间爬升 | 排除内存泄漏 |

**为什么必须自己先定**：面试官问「通过的标准是什么」，考的是有没有**验收意识**。答「压了 10 分钟没崩」是及格线；答「我先定 SLO 再压，压完逐条判定，不达标就调 max_num_seqs 再压一轮」是工程能力。

#### ② token 成本分析（公式现在就能背下来）

```
每百万 token 成本 = (1e6 / 吞吐_tok_per_s) × 单卡时价 / 3600
```

三个必答的追问方向：

- **输入输出不同价**：prefill 是算力密集、decode 是显存带宽密集，所以 prompt token 与生成 token 成本不同。这是各家 API 输入便宜、输出贵 3—4 倍的根本原因。
- **成本随并发变化**：batch 变大 → 吞吐上升 → 单 token 成本下降，但 p95 延迟上升。**成本与延迟是一对矛盾，不是两个独立指标。**
- **KV cache 挤占**：并发越高，KV cache 占的显存越多，可用 batch 反而受限 → **成本曲线的拐点在这里**，不在算力。

#### ③ KV cache 卸载（offload）

会答「显存随 N 线性增长」只是入门，被问「卸载」才是分水岭。三种层次：

| 层次 | 做法 | 代价 |
|---|---|---|
| 前缀复用（prefix caching） | 相同 system prompt 的 KV 只存一份 | 只对共享前缀有效 |
| 驱逐 / 重算 | 丢掉最久未用的 block，需要时重算 | 重算 = 重新 prefill，出现延迟尖峰 |
| CPU offload | 不活跃序列的 KV block 换到内存，需要时换回 | PCIe 带宽成瓶颈，只适合长尾 / 多轮空闲 |

一句话收口：**卸载不是免费的省显存，它把显存压力换成了带宽压力和延迟抖动。** 真实系统的优先级是「前缀复用 > 驱逐重算 > CPU offload」。

### 一个明确不补的：TensorRT

判断：**不补。** 三条理由：

1. TensorRT-LLM 要按「模型 + 卡型」编译引擎，6GB 笔记本卡上编译极慢且容易失败
2. 它和 vLLM / SGLang 是两条技术栈，同时学是两份成本换一份收益
3. 被问就诚实答：没做过 TensorRT-LLM，我用 vLLM / SGLang，理由是免编译、生态对齐 HF

但必须能说出一句话区别：**TensorRT-LLM 是编译期优化（kernel fusion、按卡型生成引擎，峰值性能高但部署僵），vLLM 是运行期优化（PagedAttention + 连续批处理，通用性好）。**

### 岗位画像修正（本次面经最有价值的一条）

| | 算法岗 | AI Infra 岗 |
|---|---|---|
| 理论追问 | 狠（「不问了解吗，直接问为什么」） | 少 |
| 工程追问 | 中（可验证性四连问） | **狠**（什么卡、几张、怎么压、标准是什么） |

## 8. 2026.11.02 面经：Agent 方向 4 题

四道题有个共同点：**不给具体方案的答案都不及格**。面试官要的是「你依据什么做决定」，不是「有哪些选项」。

### Q1 PDF 里同时有表格和图片，怎么保住表结构和图片内容

#### 先说结论

**结构信息必须显式写成文字，否则它在检索里等于不存在。**

embedding 只吃纯文本。合并单元格、表头、标题层级这些东西，一旦没被写成文本，检索时就没有任何痕迹——你后面再怎么调 rerank 都救不回来。

#### 表格的三条处理原则

| 原则 | 做法 | 不这么做会怎样 |
|---|---|---|
| 整表优先，不按长度硬切 | 先用 `pdfplumber` / `Camelot` 提取成 DataFrame，转 markdown 表格，整表当一个 chunk | 按 512 字切会把表头和数值切断 |
| 必须切时，每块重复表头 | 超长表按行分组，每组都把表头行带上 | 「2023 年营收 12 亿」脱离表头就变成没有主语的「12 亿」 |
| 给表生成一句文字摘要，拼在正文前 | 用 LLM 生成「该表为 XX 公司 2020—2023 年分业务营收，单位万元」 | 表格数字的 embedding 极弱，纯靠向量检索基本召不回 |

第三条最容易被忽略，但它往往是表格题能不能召回的分水岭。**检索匹配的是语义，数字本身几乎没有语义。**

还有一个坑要主动说：**向量检索对数字近乎无效。** 问「2023 年营收多少」，向量召回经常输给一段文字叙述。所以表格类知识必须配 **BM25 关键词检索做混合**，靠字面命中补齐。

#### 图片的两条处理原则

1. **不要只做 OCR。** OCR 把图变成一串无序文字，图里的结构（哪个数字属于哪一列）全部丢失。
2. **用多模态模型把图转成结构化文本**：
   - 图表（柱状/折线）→ 让它读出数值表，输出 markdown 表格
   - 示意图/流程图 → 输出「图中三个模块 A→B→C，A 的输出是 B 的输入」这类关系描述
   - 照片 → 输出 caption
3. 原图存对象存储，URL 放进 metadata。**回答时引用原图，而不是复述描述**——描述会丢细节，引用可以让用户自己看。

#### 还要带上层级 metadata

每个 chunk 除了正文，存 `{文档名, h1, h2, h3, 页码}`。检索时把标题路径拼到 chunk 前面再算 embedding，这叫 **contextual chunk**（给块补上下文）。

理由：一个 chunk 写着「准确率提升到 0.87」，脱离「第三章 · 消融实验」这个标题，它和「第四章 · 结论」里的 0.87 无法区分。

#### 一句话收口

**表格当结构处理，图片当内容翻译，两者都要补一句人话摘要，并且都靠混合检索兜底。**

### Q2 回答效果不好怎么办：换 API 是错的做法

#### 为什么不能换 API

换了之后**所有变量同时变了**：模型能力、prompt 适配度、上下文窗口、成本、延迟。你无法回答「是模型变强了还是运气好」，也无法向老板证明这次改动值不值。

而且换 API 不解决检索问题——**如果正确文档压根没被召回，换成 GPT-5 也答不对。**

#### 正确做法：五层定位，先找到断点

RAG 一条链有五段，每段有各自的指标：

| 层 | 指标 | 不达标说明 |
|---|---|---|
| ① 召回 | Recall@5 | 正确文档没进候选集 |
| ② 排序 | MRR / 正确文档的名次 | 进了但排太靠后，被截断 |
| ③ 上下文 | 实际进入 prompt 的 token 数、关键段是否被截 | 塞了但被截断或落在中间被忽略 |
| ④ 生成 | 答案正确率、引用准确率 | 上下文够了但答错 |
| ⑤ 拒答 | 不可回答题的拒答率 | 该说"不知道"时硬编 |

#### 最省事的分层实验（这道题的核心）

**把「正确文档 + 原问题」直接喂给模型。**

```
结果 A：它还答错  →  断点在 ④ 生成层（prompt / 模型能力 / 指令遵循）
结果 B：它答对了  →  断点在 ①②③ 检索侧
```

这一步叫 **oracle retrieval 对照**（用"理想检索结果"当上界）。它把"两个可能的原因"一刀切成一个，成本是十分钟，不用改任何代码。

**这就是单变量隔离**——和你 W12 做消融、W7 做单头多头对照是同一套方法论，只是换了对象。

#### 定位到层之后再谈方案

| 断点 | 方案 |
|---|---|
| ① 召回低 | 换 embedding 模型、混合检索（BM25+向量）、查询改写、加同义词 |
| ② 排序差 | 加 rerank（cross-encoder）、调整 top-k |
| ③ 上下文 | 调 chunk 大小、small-to-big、压缩、把关键段放首尾 |
| ④ 生成 | 改 prompt 给约束、要求先引用再回答、换更大模型 |
| ⑤ 幻觉 | 强制引用 + 无依据时拒答 |

**注意 ④ 才是唯一该考虑换模型的地方，而且它排在最后。** 前面三层不修，换模型只是把错误藏得更深。

#### 一句话收口

**先做 oracle 对照找到断点，再动那一层。换 API 是最后一层的手段，不是第一反应。**

### Q3 token 成本分析怎么做（Agent 版）

Infra 面经也问了同一题（见第 7 节），说明这是跨岗位通用考点。Agent/RAG 场景多了两块，要分开算。

#### 成本由三块组成

| 块 | 计费对象 | 特点 |
|---|---|---|
| 模型调用 | 输入 token + 输出 token，分开计价 | 输入便宜、输出贵（prefill 算力密集 vs decode 显存带宽密集） |
| 向量化 | 建库时 embedding + 每次查询 embedding 问题 | 一次性 + 每次，量级差很多 |
| 存储与检索 | 向量库内存/磁盘、对象存储 | 按 GB·月，通常最小的一块 |

#### RAG 特有的那个放大效应

**输入的 token 数被检索上下文放大 k 倍。**

按 top-k 取 5 个 chunk、每块约 512 token 算，一次查询光上下文就是约 2500 token，而用户的问题本身只有十几个 token。

**所以 RAG 的成本结构是「输入主导」，不是「输出主导」。** 这和纯对话场景完全相反，很多人算错就错在这里。

#### 三个优化手段及代价

| 手段 | 省什么 | 代价 |
|---|---|---|
| 降 top-k | 直接按比例省输入 | 召回率下降，可能漏掉正确文档 |
| rerank 后只留前 2 条 | 输入砍一半以上 | 多一次 rerank 调用（便宜但增加延迟） |
| 前缀缓存（prefix caching） | system prompt + 固定指令的重复部分 | 只有共享前缀有效 |

#### 口算模板（面试可以直接说）

```
单次查询成本 = 输入 token 数 × 输入单价 + 输出 token 数 × 输出单价
输入 token 数 = 系统指令 + k × 每块 token 数 + 问题
月成本 = 单次成本 × 日活 × 人均次数 × 30
```

**关键是能报出「输入里有多少是检索上下文」。** 说不出这个比例，说明没真算过。

### Q4 意图识别怎么做

#### 三档方案的真实取舍

| 方案 | 延迟 | 单次成本 | 准确率 | 适用 |
|---|---|---|---|---|
| 关键词 / 正则 | 微秒级 | 约 0 | 低，只能覆盖封闭集 | 高频固定意图、兜底 |
| 小模型分类（BERT 微调） | 十几毫秒 | 极低 | 有标注数据时很高 | 意图集合固定、量大 |
| LLM 判断（few-shot / function calling） | 几百毫秒到 1 秒以上 | 高 | 高，能处理开放意图 | 意图长尾、冷启动、需要给出理由 |

**面试官问这题，是想听你会不会「按场景选」，不是听你背三个选项。**

#### 工程上的正确答案是分层级联（cascade）

```
第一层：规则/关键词  →  命中即返回（拦掉高频明确意图，零成本零延迟）
第二层：小模型分类    →  置信度 >= 阈值才采纳
第三层：LLM 兜底      →  只处理剩下的小部分
```

**核心思想：用便宜的挡在前面，贵的只处理长尾。** 这个架构在推理服务里叫 routing，在缓存里叫多级缓存，是同一个套路。

#### 比准确率更重要的两个指标

**① 看混淆矩阵，不看总准确率。**

错分的代价不对称：把「退款」识别成「咨询」只是多问一句；把「咨询」识别成「退款」可能直接触发退款流程。**所以对高代价意图看召回率，不看总体准确率。**

**② 多意图要允许并列输出。**

真实用户一句话常有多个意图（「我要退款，顺便问下发票怎么开」）。强行归一选一个，必然丢一个。输出 top-2 加阈值过滤更实用。

#### 真正的难点不是分类，是意图体系设计

三类问题必须在动手前定：

- **几类？** 太粗（10 类）互相混淆，太细（200 类）标注成本和长尾噪声都爆炸
- **粒度到哪？** 「查订单」和「查物流」算不算两类
- **未登录意图怎么办？** 必须有「其他/转人工」这一类，否则模型会把新意图硬塞进旧类

**这一条最容易在面试里加分**：大多数人只会讲模型选型，讲不出「意图体系怎么定」。

## 9. 2026.11.02 面经：长鑫存储 AI 开发一面（9 题，开发八股主导）

这份面经的价值不在新知识，在于**把一件事从推断变成了实证**：所谓「AI 开发 / AI 应用」岗，考的是**后端开发基础 + Agent 概念**，算法理论只占很小一块。

| # | 题目 | 归类 | 我们覆盖 |
|---|---|---|---|
| 1 | 自我介绍 | — | — |
| 2 | Java 线程 vs 进程、线程管理与创建过程 | 操作系统 / 并发 | ❌ 支线未覆盖 |
| 3 | 死锁的定义、四个必要条件、解决思路 | 操作系统 / 并发 | ❌ 支线未覆盖 |
| 4 | 线程相关问题怎么排查和定位 | 工程调试 | ❌ 支线未覆盖 |
| 5 | RAG 切分策略与调优 | RAG | ✅ 第 8 节 Q1 + W15 |
| 6 | ReAct 与 workflow 的区别与选择 | Agent | 🔵 W17 |
| 7 | harness 是什么，与大模型什么关系 | Agent 架构 | ❌ 全新概念 |
| 8 | 「模型变强后 harness 会变薄甚至被取代」是否正确 | 观点判断题 | ❌ 需准备 |
| 9 | 浏览器输入 URL 到页面显示经历什么 | 网络 | ❌ 支线原排最后 |

### 关键判断：不学 Java，但这三题必须答得出来

第 2—4 题写的是 Java，**但考的概念与语言无关**。线程 / 进程的划分、死锁的四个条件、竞态条件的排查方法，在 Python 里有完全对应的东西。用 Python 答，面试官不会扣分——他要的是概念，不是语法。

| 题 | Python 侧的对应 | 一句话答案 |
|---|---|---|
| 线程 vs 进程 | `threading` vs `multiprocessing` | 进程有独立地址空间，线程共享；切换成本进程高；通信进程要 IPC/序列化，线程直接读写共享变量（也因此要加锁） |
| 线程创建过程 | `Thread(target=...).start()` | 分配栈 → 注册运行状态 → 交给 OS 调度器；就绪 → 运行 → 阻塞 → 就绪 |
| 死锁四个必要条件 | 同一套理论 | 互斥、持有并等待、不可剥夺、循环等待 |
| 死锁解决 | 破坏任一条件 | 工程上最实用的是**按固定顺序加锁**（破坏循环等待）＋ **加超时**（`lock.acquire(timeout=...)`，破坏不可剥夺） |
| 线程问题排查 | `py-spy dump`、`faulthandler`、`logging` + `traceback` | 先看**线程栈**判断卡在哪；死锁看是否多个线程在等同一组锁；CPU 打满看是不是忙等 |

**「排查」这题的正确答法是给流程，不是给工具名：**

```
① 先判断现象类型：卡死 / CPU 打满 / 内存涨 / 结果错
② 卡死 → dump 所有线程栈，找互相等待的锁环
③ CPU 高 → 采样火焰图，找热点函数（不是死锁）
④ 结果错 → 查共享变量有没有未加锁的读改写（竞态）
⑤ 复现：把并发数调小、加随机睡眠放大时间窗
```

**第 ⑤ 条最能加分**：多数人只会说"用工具看"，能说出"怎么让它稳定复现"的很少。

### ReAct vs workflow：选择判据

| | workflow | ReAct |
|---|---|---|
| 控制流 | 预先定义（DAG / 状态机），路径固定 | 模型每步自己决定下一步调什么工具 |
| 可预测性 | 高 | 低（同样输入可能走不同路径） |
| 成本 | 可估算 | 不可估算（步数不定） |
| 调试 | 容易（每步已知） | 难（要回放整条轨迹） |
| 适合 | 路径可枚举、错误代价高、要审计 | 路径开放、需要探索、工具组合未知 |

**选择原则一句话：能用 workflow 解决的就别上 ReAct。**

理由不是保守，是三条硬账：
1. **成本不可控**：ReAct 的步数由模型决定，一次跑 3 步和跑 30 步成本差一个量级
2. **不可审计**：金融、医疗、企业内部流程要求"同一输入走同一条路"，ReAct 天然做不到
3. **错误会累积**：每步有 5% 的错，10 步串起来只剩六成正确率

**混合做法（真实项目常用）**：外层用 workflow 固定骨架，只在某个「需要判断」的节点内嵌一次 ReAct。这叫 **workflow 包 agent**。

### harness：这一题是全场最有含量的一题

#### 是什么

**harness（脚手架 / 外壳）指模型之外、把它接到真实世界的那一整层工程。**

具体包含：

| 组成 | 干什么 |
|---|---|
| 工具定义与调用协议 | 告诉模型"你能调哪些函数、参数是什么" |
| 主循环 | 收模型输出 → 执行工具 → 把结果塞回上下文 → 再问模型 |
| 上下文管理 | 裁剪、压缩、摘要，防止超出窗口 |
| 权限与沙箱 | 哪些操作需要确认、哪些目录不许碰 |
| 失败恢复 | 工具报错后重试、换路、降级 |
| 评测与留痕 | 记录轨迹、回放、算成功率 |

一句话：**模型是「能力」，harness 是「把能力接到现实世界的接口 + 约束」。**

#### 和大模型的关系

**同一个模型，换 harness，效果能差出十几个点。** 这是这一题最关键的一句——它说明 harness 不是"包装"，是独立的生产力来源。

直觉类比：模型是一个很聪明但不熟悉你公司的人，harness 是他的工位、权限、操作手册和检查清单。人再聪明，没有权限也改不了文件。

#### 「模型变强后 harness 会变薄甚至被取代」——这个观点对一半

**三段式答案（可以直接背）：**

**① 结论：会变薄，但不会被取代。**

**② 机制：变薄的部分和吃不掉的部分是两类东西。**

会被模型吃掉的是「教它怎么做」：
- 以前要手写 CoT（思维链）模板 → 现在模型自己会分步推理
- 以前要 few-shot 塞示例 → 现在指令跟随足够好
- 以前要把任务拆成多个 prompt → 现在一次就能规划

吃不掉的是「替它负责」：
- **权限**：模型再强也不能自己决定"能不能删这个库"
- **审计**：出了事要能回答"它第几步做了什么"
- **确定性**：同一输入必须走同一条路（合规要求）
- **成本上限**：不能让一次请求跑出 30 步
- **失败恢复**：工具挂了要重试/降级，这不是智能问题

**③ 后果：harness 的重心会转移，不是消失。**

```
过去：教模型怎么做（prompt 工程、步骤拆解、示例）
将来：约束模型不许做什么（权限、沙箱、预算）+ 验证它做对了没（自动化评测、回归）
```

再补一句能压住场的：**模型越强，能做的事越多，爆炸半径越大，需要的约束面反而越宽。** 所以"变薄"指的是「教导层」变薄，「约束层」和「验证层」是在变厚的。

### 浏览器 URL 全流程：这是网络第一高频题，必须补

原系统支线把网络排在最后，理由是"面经没出现过"。**现在出现了一次，而且是这种大综合题——它的价值在于一道题串起 DNS、TCP、TLS、HTTP、服务端、渲染六块。**

答题骨架（按顺序，每段一句，不要展开太细）：

```
① 解析 URL → 查缓存（浏览器 → 系统 → 路由器）
② DNS 解析：域名 → IP（递归查询，本地 DNS → 根 → 顶级 → 权威）
③ TCP 三次握手（为什么不是两次：防止历史连接、同步双方序号）
④ TLS 握手（HTTPS）：证书校验 + 密钥协商
⑤ 发 HTTP 请求（方法、头、cookie）
⑥ 服务端：负载均衡 → 应用 → 缓存/DB → 返回响应
⑦ 浏览器渲染：HTML → DOM，CSS → CSSOM → 合成 render tree → layout → paint → 合成
⑧ 连接复用 / 关闭（keep-alive）
```

**面试官真正想听的两个点**：
- **三次握手为什么不是两次**（能答出"防止已失效的连接请求突然到达"就是及格，能说出"两次无法确认客户端接收能力"是加分）
- **渲染阻塞**：CSS 阻塞渲染、JS 阻塞解析（`defer` / `async` 的区别）

## 10. 2026.11.02 面经：科大讯飞 AI 全栈开发 HR 面（9 题）

### 先理解 HR 面在筛什么

HR 不判断"答案对不对"，判断三件事：

| 筛什么 | 对应题目 | 潜台词 |
|---|---|---|
| **稳定性** | 保研本校、湖南→合肥、offer 情况、看重什么因素 | 会不会干半年就跑 |
| **真实性** | github、项目为什么做、多少人用过 | 简历上的东西是不是你做的 |
| **自我认知** | 性格、怎么看 Agent、怎么理解 AI 全栈 | 知不知道自己弱在哪，能不能合作 |

**技术面看你"会不会"，HR 面看你"可不可信"。** 所以 HR 面的答案不需要漂亮，需要**具体 + 有代价**。

### 三道最容易答砸的题

#### ① 为什么保研本校，而不是其他学校

**这是陷阱题。** 答"求稳""没考上更好的""本校比较熟悉"——全部指向一个结论：**这个人没有向上爬的动力**。

正确结构：**主动选择 + 具体理由 + 时间成本换算**。

```
我本科就在这个学校，导师的方向是机器学习/数据挖掘，和我现在做的 AIGC 是对得上的。
换学校的边际收益主要是学校牌子，但代价是重新适应课题、重新攒数据、可能换方向。
我算过一笔账：留下来，我从大四就能开始跑实验，比换学校早一年进入有效工作。
对我这个方向来说，一年的实验积累比学校牌子值钱。
```

**关键在最后一句**——它把"没走"解释成了"算过账之后的取舍"，而不是"走不了"。

#### ② 你的 XX 软件有多少人用过

**压力题，在验证"你说的项目到底有没有真实用户"。**

**绝对不能编数字。** 面试官可能追问"在哪能看到""留存多少"，一句就穿。而且这是 HR 面，诚信记录会传回业务面。

诚实 + 转化：

```
这个项目没有对外发布，是我自己用的工具/研究性质的代码。
所以"用户数"这个指标我给不出来，这是它的短板。
但我在交付标准上按"陌生人能跑"做的：README 里有完整运行命令、有 smoke test、有性能数字。
我的判断是，一个只有作者自己能跑的项目，和一个别人能复现的项目，价值差很多。
```

**核心动作：承认指标缺失 → 换成另一个可验证的维度 → 说明你为什么这么选。**

#### ③ 你怎么理解 AI 全栈开发

**这是岗位匹配题，答好了直接加分。**

不要背岗位 JD。用**已完成的三块**证明"全栈"对你不是名词：

```
我理解的全栈不是"什么都会一点"，是一条链上每一段都能自己打通：
数据与微调 → 服务化 → 部署与监控。

我这三个项目正好各占一段：
· 微调：领域问答的 LoRA 微调，配评测集和消融，能说清 rank 怎么选
· 服务化：RAG + Agent，用 FastAPI 暴露接口，有工具调用和失败重试
· 部署：vLLM + Docker 起推理服务，Prometheus 采指标，压测出 p50/p95 和吞吐

单看每一段都不算深，但串起来我能独立把一个模型做成别人能用的服务。
我觉得这是"全栈"和"样样稀松"的区别——前者是一条通的链，后者是一堆孤立的点。
```

**最后那句是全场最该说的一句**，它把"我三个项目都浅"这个弱点提前解释掉了。

### 其余六题的一句话答法

| 题 | 答法要点 |
|---|---|
| 自我介绍 | 30 秒，三段：我是谁（研一，方向）→ 我做过什么（三个项目一句话）→ 我为什么来（这个岗位要什么，我有什么） |
| 介绍 github | 见下方专门一节 |
| 项目为什么做 | 说**触发问题**，不说"为了学习"。例：我要查自己的笔记，发现关键词搜不到语义相近的内容，所以做了 RAG |
| 怎么看 Agent 发展 | 见下方 |
| offer 情况 | 诚实：目前没有在手 offer，刚开始集中投递/在流程中。**加一句节奏**：我按计划先把基础打扎实再投，不海投 |
| 湖南为什么来合肥 | 把地域题转成公司题：不是"来合肥"，是"来讯飞"——它做的是国产大模型 + 教育/医疗落地，场景是真的 |
| 看重公司哪些因素 | 三条，按顺序：技术栈是不是真在用、有没有真实业务场景和用户、能不能看到自己的成长曲线。**薪资放最后或不提** |
| 性格 | 一个优点带一个代价，别堆形容词 |

### github 那道题：你的仓库该怎么讲

你的 `aigc-intern-roadmap` 是**学习仓库**，不是产品仓库。面试官一看就知道，所以不要试图包装成产品。

**讲法：不讲"我学了什么"，讲"我怎么验证我学会了"。**

```
这个仓库里没有产品，都是学习过程中的代码。但它的特点是我给每个结论都配了可复现的数字：

· 手写多头注意力，和 PyTorch 官方实现逐元素比对，误差 2.98e-08（验收线是 1e-5）
· 训练了一个字符级语言模型，验证集困惑度 66.48，生成脚本能从 checkpoint 独立恢复
· 单头和多头做了对照：参数量完全相同，验证集打平——我把这个反直觉的结果也写进去了

我刻意保留了失败记录，比如某个实验一开始测错了指标，结论是反的，后来改了测法。
```

**最后一句是杀招。** 绝大多数人的 github 只有成功记录，有失败记录说明你真的在做实验而不是抄代码。

### 「怎么看 Agent 发展」怎么答

这题要观点。用上一份面经学的 harness 那套直接迁移：

```
我的判断是，Agent 接下来两年的瓶颈不在模型能力，在 harness——也就是把模型接到真实世界的那层工程：
工具定义、上下文管理、权限沙箱、失败恢复、轨迹审计。

模型变强会吃掉"教它怎么做"那部分（手写 CoT、few-shot 已经不必要了），
但吃不掉"替它负责"那部分——权限、审计、成本上限、失败恢复，这些不是智能问题，是责任问题。

所以我判断未来两年的红利在工程侧，不在提示词技巧侧。
```

### 三个不能碰的坑

1. **编数字。** "有多少人用""留存多少""涨了多少"——这类问题一律宁可说没有。
2. **贬低其他公司。** 说别家"太卷""没技术"会让 HR 担心你以后也这么说他们。
3. **过度表忠心。** "我愿意加班""我可以不要钱"不是加分项，是减分项——它让人怀疑你在别处没有选择。

### 性格题模板：优点 + 代价

不要"认真负责、积极向上、抗压能力强"——这三个词所有人都说，等于没说。

模板：**一个具体行为 + 它带来的代价 + 你怎么处理这个代价**。

```
我倾向于先把不确定的东西跑一遍再决定，而不是先想清楚所有细节。
好处是很少卡在"不知道行不行"上；代价是有时会花时间在其实不需要验证的细节上。
我现在的做法是，先问一句"这个结论会不会影响后面的决定"，不会影响就先跳过。
```

**能说出自己的代价，才是可信的自我认知。**

## 11. 2026.11.02 面经：拿到腾讯 / 字节 / 阿里云 offer 的人，总结的 4 个必问

来源：一位面了二三十轮、最终拿腾讯 / 字节 / 阿里云 offer 的候选人，自己做了个面经聚合站。他给的四个高频主题是**唯一一份全部指向"工程验收"而非"模型原理"的面经**。

### 先看清这四题是同一件事

| 题 | 表面在问 | 底下在问 |
|---|---|---|
| RAG 流程 + 「答错了怎么检索」 | 你懂不懂 RAG | 你会不会**归因到具体环节** |
| 上下文压缩「怎么知道没压坏」 | 你会不会摘要 | 你有没有**验证有损转换**的方法 |
| 评测：固定任务 / 判定标准 / 调用预算 | 你会不会算指标 | 你有没有**回归意识** |
| 多 Agent 通信「已完成到哪一步」 | 你会不会写消息格式 | 你会不会**把"声称完成"变成"可检查的完成"** |

**统一主题：你怎么知道它真的做对了。**

这四题背不了——它们全部要求"你有一个跑过的系统 + 一组真实数字"。教程里学不到。

---

### Q1 RAG：追问「模型答错了，怎么从检索侧解决」

**这是一次归因追问，不是知识追问。** 面试官要看你会不会把"答错"拆到具体环节。

分层归因（沿用第 8 节 Q2 的 oracle 对照）：

```
把「正确文档 + 原问题」直接喂模型
  → 还答错：断点在生成侧，与检索无关，别乱改检索
  → 答对了：断点在检索侧，继续往下拆
```

检索侧再拆三层，顺序不能反：

| 层 | 判断依据 | 手段 |
|---|---|---|
| ① 根本没召回 | Recall@k 低 | 查询改写（同义扩展 / HyDE / 子问题拆解）、多路召回、混合检索（BM25 + 向量） |
| ② 召回了但排太后 | 正确文档名次 > k | 加 rerank（cross-encoder）、扩大 k 再重排 |
| ③ 召回对了但 chunk 里没有答案 | 人工看 chunk 内容 | 切分策略问题：chunk 太碎丢上下文 / 太大混噪声 |

**第 ③ 层最容易被漏**：多数人只想到"检索不到"，想不到"检索到了但块里没有那句答案"。

**反向验证的手法（加分项）**：拿最终错误答案去反查——如果能在库里找到一段文本能纠正它，说明是检索没召回到；如果整个库里都没有这段信息，那是知识库覆盖问题，不是检索问题。**这时候该做的是补文档，不是调检索。**

---

### Q2 上下文压缩：怎么知道没压坏

**这题考的是「有损转换怎么验证」，是个通用工程问题。**

先明确压缩为什么必须做：上下文窗口有上限、成本按 token 计、长上下文中间信息会被忽略（lost in the middle）。

**验证方法：回放 + 三类检查。**

```
留一组固定任务（10—20 条，覆盖不同类型）
压缩前后各跑一遍，比「最终产物」，不比「摘要文本」
```

三类检查，按重要性排：

| 检查 | 查什么 | 失败表现 |
|---|---|---|
| **① 禁止事项有没有丢** | 用户说过"不要动 X""必须用 Y 格式" | 压缩把否定句当废话删了 → 后续违规 |
| **② 后续步骤能不能接上** | 压缩后模型还知不知道"现在做到哪" | 重复已完成步骤，或跳过关键步骤 |
| **③ 关键证据有没有保留** | 之前核实过的事实、文件路径、ID | 模型重新去查一遍，或编一个不存在的路径 |

**第 ① 条最关键**。压缩算法天然倾向于保留"做了什么"，删掉"不许做什么"——因为否定句短、看起来信息量低。**但它是约束，丢了就全线崩。**

**工程上的三个对策**（比"怎么验证"更值钱）：

1. **结构化压缩，不做自由摘要**：固定字段（目标 / 已完成 / 待办 / 约束 / 关键证据），逐字段填，而不是让模型自由写一段
2. **约束单独存一份，不参与压缩**：约束进 system prompt 或独立状态字段，永远原样保留
3. **保留最近 N 轮原文**：只压缩更早的部分，最近几轮不动（模型最依赖近期上下文）

---

### Q3 评测：固定任务 + 判定标准 + 调用预算 + 分层拆解

四个要素缺一不可：

| 要素 | 具体做法 | 少了会怎样 |
|---|---|---|
| 固定任务集 | 一组不变的任务，跨版本复用 | 每次评测结果不可比 |
| 判定标准 | 明确"什么算通过"（含人工 rubric） | 只能看分数，不知道对不对 |
| **调用预算** | 限定 token / 步数 / 工具调用次数上限 | 模型靠"多跑 20 步"赢，成本爆炸而你没发现 |
| **多轮重复** | 同一任务跑多轮，看成功率方差 | 单次结果可能只是运气 |

**「整体变好了，但某类任务退步了」——这是最见功力的一问。**

答法三步：

```
① 按任务类型拆开看，不做总体平均
   总体准确率涨 3 个点，可能是 A 类涨 8 点、B 类跌 5 点，平均下来看不出问题
② 把退步类的失败案例全部留下，做成回归集
③ 每次改动都跑一遍回归集，退步就不许合入
```

**这一步的本质是把"评测"变成"回归测试"** —— 和第 8 节说的软件工程实践是同一个东西。

**还有一个隐性考点：判定标准本身可靠吗？**
如果用 LLM 当裁判（LLM-as-judge），要说明三件事：裁判模型是什么、prompt 怎么定、**有没有人工抽检过一致性**。答不出这三条，等于没有判定标准。

---

### Q4 多 Agent 通信：怎么定义"已完成"

**核心问题：Agent 说"我做完了"，接收方凭什么信？**

消息里必须有五个字段，缺一个就会返工：

| 字段 | 内容 | 不写会怎样 |
|---|---|---|
| **目标** | 这次要达成什么（一句话） | 下游不知道边界，做超或做漏 |
| **约束** | 不许做什么、必须满足什么 | 产出违规，返工 |
| **证据** | 哪些结论**已核实**、怎么核实的 | 下游把猜测当事实继续推 |
| **进度** | 完成到哪一步（不是"完成/未完成"） | "已完成"歧义：写完代码 ≠ 跑通 ≠ 通过评测 |
| **产物 + 验收方式** | 交付物在哪、接收方怎么检查 | 下游无法验证，只能盲信 |

**「已完成到哪一步」这问最能分人。** 提供一个可用的分层：

```
L1 计划好了      → 有步骤，没执行
L2 做出来了      → 有产物，没验证
L3 验证过了      → 跑通了，有日志/截图/数字
L4 可交付        → 陌生人按说明能复现
```
